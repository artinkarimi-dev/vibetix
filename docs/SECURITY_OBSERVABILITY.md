# Security observability

Fixed structured events include `login_failed`, `rate_limited`, `abuse_store_unavailable`, `authorization_failed`, `origin_rejected` and `booking_rejected`. They carry request ID, server-selected route template, actor ID when known, an HMAC of client IP, and an optional fixed policy/error category. They exclude submitted email/passwords, proof, cookies, tokens, request bodies, query strings and card/payment data. Broad request/error objects must never be passed to this helper.

Rate events identify global/login/register/password, identity, account hold/checkout/quote budgets. Booking rejections cover unavailable/invalid/expired holds, idempotency conflicts, invalid extras/promos; repeated holds above the budget generate rate events. This is structured visibility, not automated fraud detection or a verified-person/bot control.

Successful privileged mutations append transactional `AuditLog` rows (see `ADMIN_SECURITY.md`). Operator SQL/role/bootstrap changes require PostgreSQL/provider auditing; nonexistent refund/ticket/role application endpoints have no events to emit yet. The application does not claim a complete staff activity ledger or completed MFA deployment.

Existing request logs omit query strings and bodies and redact cookie/auth/set-cookie headers. API errors return fixed messages/request IDs; worker failures store/log generic categories. Infrastructure access logs may still contain full URLs/client addresses; review nginx/CDN/provider logs separately. Pseudonyms and actor IDs remain linkable personal metadata and need retention/access policies.

Before deployment route logs to a protected central sink, set retention/deletion and access reviews, rate-limit/sample attacker-generated events without losing aggregates, and alert on unusual failed login/403/429 rates, Redis protection 503s, audit gaps, job age/failures, DB privilege changes and backup age. Configure worker heartbeat/last-success monitoring separately from HTTP readiness. No log collector, dashboard, alert route, incident rotation or external immutable sink was provisioned. The development logger's tests check field privacy; operational alerting and full log-pipeline redaction remain unverified.


The native pre-production lab observed structured `dependency_unavailable` and `worker_iteration_failed` events as well as authentication, rate, authorization, booking and abuse-store failures. Worker failures emit a fixed event and timestamp without raw exception details. `/live` is process-only; `/ready` and the compatible `/health` alias query PostgreSQL and Redis and return a generic 503 when dependencies fail. Health probes bypass global abuse counters and should remain private to the platform. Use readiness for traffic eligibility, liveness for process management, and a separate deployed worker heartbeat/backlog check. These endpoints do not establish complete migration compatibility or worker health. See [execution evidence and remaining alert gates](PREPRODUCTION_VALIDATION_REPORT.md).


The staging sprint adds `api_request` records with fixed route template, method, status class/code and response duration. Default raw-path request logging is disabled; request metrics exclude URLs, query strings, users, headers and bodies. Existing fixed security events supply failure/budget/authorization counts. Booking emits `hold_updated`, `hold_created`, `hold_released`, `hold_conflict`, `hold_failed`, `checkout_started`, `checkout_confirmed`, `checkout_declined`, `checkout_failed` and `idempotent_replay`; count replay separately from newly committed sales. Worker expiry emits a count; lazy API expiry is not a complete expiry counter. Database/pool failures remain visible through generic request failure categories, 5xx and readiness; detailed pressure belongs in protected database/platform metrics.

The worker emits a heartbeat approximately every 15 seconds after successful iterations, with pending/failed job counts and oldest pending age, plus committed `job_processed`, `job_retry` and `job_failed` outcomes. These signals are collectable JSON, not a Prometheus server or verified external collector. Queue scans need capacity review as volume grows. Local filesystem delivery is the only implemented transport; real-provider leases/idempotency/reconciliation remain an integration gate. See [vendor-neutral alert hooks](../deploy/alert-policy.json) for thresholds, routes and operational actions. No actual alert delivery is claimed.
