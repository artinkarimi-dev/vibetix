# CI and supply-chain security

The workflow explicitly uses read-only repository contents permission, immutable verified action commit pins, disabled checkout credential persistence, a job timeout and isolated pinned PostgreSQL/Redis services. It does not deploy or access production secrets. Do not use `pull_request_target` to execute untrusted repository code or attach privileged deployment environments to PR validation.

Frozen pnpm installation, the exact package-manager version and lifecycle-script allowlist remain in force. Only necessary dependency scripts should be approved; inspect any lockfile/script/pin change. Redis and operations clients are exact-version dependencies. Current scripts replace the old per-process plugin with tested shared counters; no duplicate limiter dependency is retained.

CI runs Prisma generation/migrations/seed, both typechecks, units and backend security integrations, builds, bundle/image budgets, focused secret/security checks, dependency audit, existing Chromium QA and the live-stack browser journey. The production integration harness creates/rotates dedicated **test-only** role credentials against a `*_test` database. It must never target production. The CI bootstrap URL is intentionally powerful only inside the throwaway service; production runtime receives its restricted URL instead.

Only selected report/budget artifacts are uploaded; whole local `artifacts/` directories can contain database data and must not be uploaded. Browser reports may still contain fictional test inputs/screenshots: apply a short retention and never run them with real customer data. Deployment signing, protected environments, provenance/SBOM publication and image scans need a real registry/repository policy.

`security:check` performs high-confidence secret-pattern/connection-credential checks on selected source/configuration files, frontend output patterns and focused deployment invariants. It is not exhaustive SAST, a Git history scan or validation of secret-manager access. The local directory has no usable Git history; add a maintained history-aware secret scanner on the actual repository host after reviewing exceptions. `pnpm audit` is required and fails on reported advisories; review fixes instead of automatic force upgrades.

Dependabot configuration proposes GitHub Actions, npm and Docker updates for review. Pinning requires continued maintenance; a green dependency audit does not cover container OS vulnerabilities, malicious packages or unpublished CVEs. Remote GitHub Actions, runner/service networking and the pinned image execution have not been run locally; see the hardening report for actual commands/results.


The staging sprint adds a formatting gate, post-E2E integrity check, runtime CycloneDX component inventory, compiled/static build checksums and pinned backend/frontend image build steps to the workflow. CI image builds are configured but were not executed remotely on this host; they do not imply layer inspection or container CVE coverage. The native hot-event/outbox crash suite runs through the local `release:verify` gate with its documented tool prerequisites; the hosted workflow does not yet provision those native prerequisites or attest that load result. The top-level local command records pass/fail/not-executed stages in `artifacts/release/final-verification.json`; a remote CI job needs its own successful attestation before deployment. No registry push or production deployment was added.
